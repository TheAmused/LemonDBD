Autor wyzwania: **TheAmused**. Status: **zaimplementowane** na gałęzi `feature/id-please` (backend + frontend, bez commitów); stan wdrożenia i odstępstwa w sekcji 12. Analiza z 2026-10-28 na bieżącym stanie repo (`backend/app`, `frontend/src`), wersja 4: **wszystkie trzy tryby nieskończone, odznaka przy progu streaka**, żywy skład konta zamiast snapshotu, bramki dostępu. Algorytmy sprawdzone symulacją (sekcja 4) i testami własności (łącznie ponad 7000 łańcuchów, także 400-meczowych). Kod referencyjny w załączniku A.

## 1. Werdykt w skrócie

- **To streak bez końca.** Żaden tryb się nie „kończy”: gra się dalej, dopóki nie przegrasz, a rekordem jest `best_streak`. **Odznakę** dostaje się po osiągnięciu progu streaka: **Milestones 50, Hardcore 30, Hardcore+ 25**. Wersja z ukończeniem po 50/30/25 meczach jest wycofana, tak jak wcześniejsza „Milestones = 10 meczów”.
  - **Milestones**: checkpoint co 10 meczów (5 + 5), przegrana cofa do ostatniego checkpointu. Odznaka przy streaku 50.
  - **Hardcore**: bez checkpointów, przegrana = od nowa. Odznaka przy streaku 30.
  - **Hardcore+**: bez checkpointów, bardziej „zakręcony” wzór i **pamięć postaci** (każda postać strony pojawia się raz na „rundę” N meczów). Odznaka przy streaku 25.
- **Odznaka jest trwała.** W chwili pierwszego osiągnięcia progu zapisujemy jeden `ChallengeCompletionRecord` (wariant `milestones` / `hardcore` / `hardcore_plus`) **bez kończenia runu**. Dzięki temu półka trofeów, plakietki na kartach i historia ukończeń działają bez zmian, a odznaka nie znika po porażce, abandonie ani resecie próby (sekcja 6).
- **Bez zamrażania.** Lista postaci i perków jest brana na żywo z konta przy każdym kroku. Zmiana posiadania w trakcie biegu odświeża dane sama. Ma to konsekwencje opisane w sekcji 5 (odtwarzalność ciągu, „wędkowanie”); trzeba je znać, ale da się z nimi żyć.
- **Czysty mirror nie działa** (mecz 3 = mecz 1 w 100% przebiegów). Mirror zostaje jako **mecz 2** (to jest dusza wyzwania), a od meczu 3 wchodzi splot streaka, postaci i perków. Sama arytmetyka, bez losowania i bez hashy.
- **Bramki dostępu**: Hardcore wymaga min. 25 survivorów i 20 killerów, Hardcore+ 30 i 30, plus odpowiednia liczba odblokowanych perków (sekcja 6). Milestones zostaje na obecnym minimum konta.
- **Wszędzie**: karta w zakładkach Survivor, Killer i Survivor/Killer, z grafiką zależną od miejsca (S0/K0 na karcie, S1/K1 Milestones, S2/K2 Hardcore, **S3/K3 Hardcore+**) i od strony bieżącego meczu w nagłówku planszy. Strona startowa jest podpowiedziana zakładką, a w zakładce Survivor/Killer wybierana.
- **Co poprawił audyt kodu (wersja 4):** (1) reset admina kasuje także rekordy ukończeń, więc odznaka znika (plan twierdził odwrotnie); (2) brakowało eksportu i importu bazy (`export_writer`, `import_community`, `scraperTargets.ts`); (3) `_reset_to_fresh` rzuca błąd dla kolumn bez jawnej wartości (kolumny JSON); (4) `/result` bez `match_number` pozwalało podwójnym kliknięciem przeskoczyć dwa mecze; (5) istniejące zapytania o posiadanie sortują po nazwie i ładują cały katalog, a frontendowy `useOwnedRoster` po numerze wydania, więc potrzebne własne lekkie listy i endpoint `/roster`; (6) `active_runs` i kafelki (`disabled`, `disabledBadge`) dla trybu nieskończonego; (7) pełna lista etykiet trybu w panelu admina i w 5 językach; (8) sprzątanie nieaktywnych runów w setupie; (9) logi przycinane do 100, więc stan łańcucha leży w runie. Pełna lista podpięć: sekcje 8 i 9.
- Skala: nowa para tabel (run + log meczów), jeden serwis, jeden blueprint, kilkanaście podpięć (sekcje 8 i 9), 5 języków. Pięć faz (sekcja 10).

## 2. Jak wyzwania działają dziś

### Backend
- Każdy tryb ma **własny model runu** z mixinów `ChallengeRunMixin` → `RetryableRunMixin` → `StreakRunMixin` (`models/challenge_mixins.py`; `StreakRunMixin` daje `current_streak`, `best_streak`, `last_checkpoint_streak`) i **własny log meczów** (`MatchLogMixin`/`StreakLogMixin`). Run to jeden wiersz na `(user_id, wariant)`.
- Serwis dziedziczy z `StreakRunService` (`services/streak_run.py`): find-or-create, abandon (zachowuje logi i `attempt`), blokada wiersza przed `submit_result`, zapis ukończenia.
- Endpointy `run`, `reveal`, `run/abandon`, `stats`, `completions` generuje `make_streak_blueprint` (`core/streak_blueprint.py`). Ręcznie napisany jest tylko `POST /result`. Blueprint sprawdza też weryfikację e-maila.
- **Checkpointy już istnieją**: `ChaosRun` (poziom „medium”) ma interwał 10 (`CHAOS_CHECKPOINT_INTERVAL`), po wygranej na wielokrotności interwału zapisuje `last_checkpoint_streak` i stan z checkpointu, a po przegranej wraca do niego (`_compute_loss_outcome`). Milestones kopiuje ten wzorzec.
- Obecne tryby **zamrażają pulę** (`owned_killer_ids`, `unlocked_perk_ids` w runie, `_refresh_if_untouched`). „ID, Please” celowo tego **nie robi** (Twoja decyzja), więc ten mechanizm nie jest używany; serwis sam czyta żywy skład.
- Ukończenie zapisuje `ChallengeCompletionRecord(mode, variant, attempts_taken, matches_played, unlocked_characters_count, full_roster)`. Z tej tabeli biorą się trofea i plakietki.
- Kill switch: `CHALLENGE_MODES = ("gauntlet", "chaos", "history", "page_streak")` w `models/admin.py`. `assert_challenge_mode_enabled(mode)` pilnuje każdego zapisu.
- Inne miejsca znające listę trybów: `challenge_reset.py`, `challenge_reset_email.py`, `streak_cleanup_service.py` (kara za 90 dni bezczynności), `streak_stats.py`, `user/data_export.py`, `db/export_registry.py`, `challenge_completions.py` (`fetch_active_run_variants_by_mode`), `models/__init__.py`.
- Migracje: Alembic, ręczne, idempotentne (`0032_user_preferences.py` to wzór). `create_all()` buduje świeże bazy.
- Obowiązują: limit 600 linii na plik (guard), testy na właściwym poziomie (CLAUDE.md), `to_dict` przez `ColumnDictMixin["…Dict"]` z TypedDictami w `schemas/`.

### Frontend
- `/streaks` przekierowuje do ostatnio używanej zakładki: `killer`, `survivor` lub `challenge` (`RoleTabs.tsx`). Zawartość zakładek to `panels.ts` (`getKillerStreakPanels`, `getSurvivorStreakPanels`, `getChallengeStreakPanels`), renderowane przez `StreakPanelGrid.tsx`.
- Kliknięcie karty otwiera modal wyboru trudności (`ChallengeModeModal` + `buildCompletionTiles`) albo od razu planszę, jeśli gracz ma zapisany wybór w `streakDifficultyPrefs.ts` i run w toku. Trofea na kartach czytają `useChallengeCompletionStatus`.
- Plansza trybu (np. `ChaosBoard`) = `useChallengeRun` (jedna maszyna stanów load/mutate/busy/error) + `ChallengePanel`, `ChallengeProgress`, `StreakActionBar`, `*StatsDrawer`, `AbandonConfirmModal`, `*RulesModal`, `ChallengeCompletionHistoryDrawer`. Strona to cienki wrapper w `ChallengeModeGate`.
- Istnieje trasa dynamiczna `app/[locale]/streaks/[role]/gauntlet-streak/page.tsx` (rola z URL), więc wzorzec „ta sama karta w różnych zakładkach” jest już użyty.
- Posiadanie: `useOwnedRoster` (z licznikiem `reloadCount`) i `AuthContext.ownership` (`OwnershipSummary`).
- Teksty: `locales/{en,pl,de,es,ja}/streaks.ts` i spółka, z testami zgodności kluczy i skanem i18n.

## 3. Dane: założenia a rzeczywistość

| Założenie z rozmowy | Co jest w kodzie |
|---|---|
| ID zaczynają się od 0 | ID w bazie zaczynają się od **1** (`killers` 1–44, `survivors` 1–54, `perks` 1–321), bez luk w katalogu (sprawdzone w seedach). **Dziury pojawiają się w posiadanym podzbiorze**: konto darmowe ma killerów o ID 1, 2, 3, 4, 8, więc po ID nie da się liczyć modulo. Indeks „0…N-1” to pozycja w posortowanej liście posiadanych, czyli Twoje `a:b`. Dziurę robi też flaga `is_disabled`. |
| Perki killera i survivora w osobnych tabelach | **Jedna tabela `perks`** z kolumną `role` (Survivor 176, Killer 145 w seedzie), ID globalne 1–321. Postacie są w dwóch tabelach. Dla algorytmu bez różnicy, bo liczymy na pozycjach. |
| Perki ma gracz na koncie | `UserPerkOwnership.is_unlocked` + kaskada z posiadania postaci + perki ogólne (`is_generic_counterpart`, bez właściciela) zawsze odblokowane. Gotowe: `ownership_service.get_user_perks(user_id, category=…)`, filtr jak w Chaosie (`is_unlocked` i nie `is_disabled`). |
| Postacie ma gracz na koncie | `get_owned_killers(...)` i `get_owned_character_ids(user_id, role, ownership)`. Dla „ID, Please” bez limitu `release_number`, jak Chaos. |
| Pule mają różne rozmiary | Tak, **każdy użytkownik ma inne**. Zakres: od najmniejszego możliwego konta (5 killerów / 34 perki i 7 survivorów / 38 perków) do pełnego (44 / 145 i 54 / 176). Algorytm nie rozróżnia „pełnych” i „darmowych” kont: bierze `N` i `M` konkretnego gracza. |
| Perki zawsze dostępne | Bez właściciela lub `is_generic_counterpart`: **killer 19, survivor 17**. Każda postać uczy dokładnie 3 perków. Stąd progi z sekcji 6 (np. 25 survivorów = 17 + 25·3 = 92 perki). Liczbę „zawsze dostępnych” liczymy z bazy, nie na sztywno. |

Wniosek: matematyka działa na czterech **bieżących** listach ID z bazy, posortowanych rosnąco: `killer_ids`, `survivor_ids`, `killer_perk_ids`, `survivor_perk_ids`. **Pozycja w liście to „ID” widoczne dla gracza (od 0).** Listy nie są zapisywane w runie; czytamy je na żywo przy każdym żądaniu (sekcja 5).

## 4. Analiza algorytmu i symulacja

Skrypty: losowe otwarcia × 2 strony × 60 meczów dla pul: pełnej 44/145 + 54/176, średniej, najmniejszej, losowych rozmiarów i przeglądu 60 realistycznych kont. Wszystko to **czysta arytmetyka: zero losowania, zero hashy.** (Pierwsza wersja planu miała SHA-256, druga obrót o streak; obie wycofane: pierwsza łamała „bez losowania”, druga dawała widoczny szyk.)

| Wariant | Powtórzony loadout | „Szyk” (zestaw tej strony = poprzedni przesunięty) | Postacie |
|---|---|---|---|
| **Czysty mirror** (bez streaka) | mecz 3 = mecz 1 w 100% przebiegów | – | tylko 2 stany |
| **Szkic z załącznika** (sumy, ×31, probing) | brak pętli | – | średnia pula nierówna (χ²/df 8,3) |
| **Mirror + obrót o streak** | pełna pula 0%, najmniejsze konto 78% | **58% par = czyste przesunięcie** (15,20,30,40 → 16,21,31,41) | równe |
| **Wzór mieszany** (Milestones, Hardcore) | pełna pula **0% w 300 meczach**, najmniejsze konto 1% w 60 | **0–0,7% par** | udział 0,9–1,15 „sprawiedliwego” (najmniejsze konto 0,8–1,8) |
| **Hardcore+** (wzór + pamięć) | 0% | **0–0,01%** | **0 powtórzeń** |

Testy własności Hardcore+: 3600 łańcuchów × 60 meczów, 6 rozmiarów puli (od 44/145 po 1 postać / 4 perki). Determinizm, niezależność od kolejności klikania, 4 różne perki w zakresie, postać w zakresie, **25 różnych postaci w 25 meczach** na kontach ≥ 30 + 30. **Od meczu 3 żaden mecz Hardcore+ nie jest identyczny z meczem zwykłego łańcucha** (0 z 11 500), mecze 1 i 2 są wspólne (to rdzeń wyzwania: suma i mirror).

Pozostałe pomiary (wzór podstawowy):
- **Streak w formule jest konieczny.** Bez niego 100% przebiegów zapętla się od meczu 3. Tamten model AI miał rację.
- **Przykład z Twojej wiadomości.** Otwarcie `15, 20, 30, 40` i `16, 21, 31, 41` (survivor, pełna pula) po meczu 2 nie mają ze sobą nic wspólnego: mecz 3 to `31, 89, 147, 169` (postać 26) kontra `1, 43, 105, 167` (postać 52).
- **Centralne twierdzenie graniczne:** `suma mod N` jest równa z dokładnością ±5% przy 44 i 54 postaciach.
- **Wyjście poza zakres** załatwia `indeks mod rozmiar_listy` (survivor → killer: 176 → 145 perków, ok. 55% otwarć ma indeks ≥ 145). Zderzenia po `mod` rozwiązuje przesunięcie o 1 w górę.
- **Długie łańcuchy (tryby są nieskończone).** 150 otwarć × 400 meczów: wzór podstawowy bez pętli identycznego loadoutu na pełnej puli i na minimum Hardcore+ (30/109 · 30/107), także Hardcore+ (0 z 150). Hardcore+ na minimalnej puli Hardcore (20/79 · 25/92), której nie dotyczy, miał 1 pętlę na 150 (od meczu 103), ale ten tryb tam nie działa. **Pamięć w Hardcore+ działa w rundach:** w każdym kolejnym oknie N meczów danej strony (N = liczba postaci tej strony) pojawia się każda postać dokładnie raz (sprawdzone asercją na wszystkich oknach 400-meczowych łańcuchów); po zagraniu wszystkich pamięć się zeruje i zaczyna się nowa runda.
- **Powtórki postaci we wzorze podstawowym są możliwe** (~98% przebiegów w 20 meczach na stronę, tyle co losowanie ze zwracaniem). W Milestones i Hardcore to akceptowane; Hardcore+ ma pamięć.
- **Przegląd 60 realistycznych kont:** powtórzony loadout nie wystąpił w 51 z 60 kont, najgorsze konto 2%. Najmniejsze możliwe konto: 1%.
- **Ile da się policzyć z góry.** Wzór podstawowy to kilkanaście działań z poprzedniego meczu: da się na kartce, ale bez wzoru widocznego gołym okiem. Hardcore+ ma iloczyny sąsiadów, `s³` i mecz sprzed dwóch; to już raczej skrypt niż kartka. Kto napisze skrypt, policzy cały ciąg; ukrycie tego wymagałoby elementu niejawnego, którego nie chcesz.

## 5. Specyfikacja mechaniki

### Wzór podstawowy (Milestones, Hardcore)
Oznaczenia: `N` = liczba postaci strony, `M` = liczba perków strony (z **bieżących** list), `s` = aktualny streak (numer właśnie wygranego meczu w próbie), `c` = pozycja postaci z poprzedniego meczu. „Wpasuj” = weź `mod M`, a gdy wartość już jest w zestawie, idź o 1 w górę (też `mod M`); wynik ma zawsze 4 różne wartości.

1. **Mecz 1** (strona startowa): postać = `(suma 4 ID) mod N`.
2. **Mecz 2** (druga strona): perki = ID z meczu 1 przeniesione na drugą stronę (**mirror**, wpasuj do `M`); postać = `(suma tych ID) mod N`. To Twoje „ID 9 survivor → ID 9 killer”.
3. **Mecz 3 i dalej** (`s ≥ 2`). `P0..P3` = ID poprzedniego meczu wpasowane do `M` tej strony (rosnąco), `T` = ich suma:
   - perk `j` (0..3) przed wpasowaniem: `Pj · (s + 2) + T + j · (c + 1) + s²`, potem wpasuj;
   - postać: `((suma nowych ID) · (s + 1) + c + T) mod N`.
4. Strony przeplatają się: start, druga, start, druga…

### Wzór Hardcore+ (zakręcony, z pamięcią)
Mecze 1 i 2 jak wyżej (suma i mirror). Od meczu 3 (`s ≥ 2`), dodatkowo: `U0..U3` = perki meczu sprzed dwóch (**ta sama strona co nowy mecz**), `cu` = jego postać:
- perk `j` przed wpasowaniem: `Pj·(s+2) + P(j+1)·P(j+2) + U((j+s) mod 4)·(s+3) + s³ + T + j·(c+1) + cu·(j+2)`, potem wpasuj (indeksy `j+1`, `j+2` mod 4);
- postać: `((suma nowych ID)·(s+1) + T·(cu+1) + c·s + (suma U) + s²) mod N`;
- **pamięć:** jeśli postać była już w tej rundzie na tej stronie, bierzemy **następną wolną** (`+1 mod N`). Gdy zagrano już wszystkie `N` postaci strony, pamięć tej strony się zeruje i zaczyna się nowa runda (funkcja z załącznika A jest czysta: gdy zbiór jest pełny, traktuje go jak pusty; **zerowanie zapisanego zbioru robi serwis** przy zapisie meczu). Tryb jest nieskończony, więc rundy się powtarzają; przy wymaganiu ≥ 30 postaci runda trwa ≥ 30 meczów danej strony, czyli ponad 25 meczów odznaki to jeszcze pierwsza runda.

Czym różni się od podstawowego: iloczyn sąsiednich perków (nieliniowość), sześcian streaka, wiązanie z drugą „nogą” łańcucha (mecz sprzed dwóch), postać zależna od postaci sprzed dwóch, brak powtórzeń postaci.

Przykład (pełna pula, start Survivor, perki `15, 20, 30, 40`, wzór podstawowy):

| Mecz | Strona | Postać (pozycja) | Perki (pozycje) |
|---|---|---|---|
| 1 | Survivor | 51 | 15, 20, 30, 40 |
| 2 | Killer | 17 | 15, 20, 30, 40 |
| 3 | Survivor | 26 | 31, 89, 147, 169 |
| 4 | Killer | 32 | 12, 20, 74, 101 |
| 5 | Survivor | 43 | 24, 29, 48, 119 |

### Żywy skład konta (bez zamrażania)
Zasada: **nic o liście postaci i perków nie jest zapisane w runie.** Run trzyma tylko mecz w toku, jako **ID z bazy** (nie pozycje), a pozycje wylicza na żywo z bieżących list.

- **Skąd lista:** postacie `is_owned` i nie `is_disabled`; perki `is_unlocked` i nie `is_disabled`; cztery listy posortowane rosnąco po ID z bazy. Czytane w każdym żądaniu (jak Chaos czyta `get_user_perks`).
- **Mecz w toku jako ID z bazy:** `current_loadout = {side, character_id, perk_ids[4]}`. UI pokazuje pozycje („ID”) przeliczone na żywo, więc dokupienie killera o niskim ID przesuwa wyświetlane ID wszystkich wyższych. Zapisany mecz nie zmienia się sam: postać i perki dalej są te same.
- **Następny mecz po wygranej:** ID poprzedniego meczu → pozycje w **bieżącej** liście (`bisect_left`, przycięte do końca listy) → funkcja z załącznika A → wynik z powrotem na ID z bazy → zapis. Jeśli poprzedni perk albo postać już nie jest posiadana, `bisect` daje najbliższego wyższego sąsiada, a ewentualne zderzenia załatwia „wpasuj”. Przetestowane: wynik zawsze ma 4 różne poprawne perki, nic się nie wywraca (np. po odznaczeniu 10 perków perki z tej dziury trafiają na tę samą pozycję i `wpasuj` je rozdziela).
- **Otwarcie (mecz 1):** klient wysyła 4 pozycje razem z **odciskiem list** (rozmiary czterech list + suma kontrolna ID; służy tylko do wykrycia zmiany i nie wpływa na ciąg). Serwer porównuje odcisk z bieżącym. Różnica → `409 roster_changed` z odświeżonym stanem, bez żadnej straty. Chroni to przed sytuacją „zmieniłem posiadanie w drugiej karcie i zatwierdziłem 4 inne perki, niż widziałem w kalkulatorze”.
- **Odświeżanie w UI:** `useIdPleaseRun` ponownie pobiera stan przy powrocie na kartę (`visibilitychange`/focus), po każdej akcji i po zmianie posiadania w aplikacji. `AuthContext.ownership` i `useOwnedRoster` (`reloadCount`) już istnieją; w fazie 3 trzeba sprawdzić, czy zapis posiadania na stronie postaci odświeża `ownership`, a jeśli nie, dodać zdarzenie. Dodatkowo odcisk w odpowiedzi `/run` pozwala UI zauważyć zmianę.
- **Hardcore+ (pamięć) na żywo:** `used_character_ids` trzyma ID z bazy per strona. Przy liczeniu zamieniamy je na pozycje w bieżącej liście, pomijając postacie, których już nie ma.
- **Checkpoint (Milestones):** `checkpoint_loadout` to mecz, od którego zaczyna się następny odcinek, zapisany jako ID z bazy. Po przegranej run wraca do tego zapisanego meczu, a kolejne są liczone na żywo od nowa.

**Konsekwencje, które warto znać (wybór „bez zamrażania” je niesie):**
1. **Odtwarzalność tylko przy niezmienionym składzie.** Te same 4 perki dają zawsze ten sam ciąg, o ile posiadanie się nie zmieniło. Zmiana w środku biegu zmienia **kolejne** mecze (już zagrane i bieżący zostają).
2. **„Wędkowanie”.** Następny mecz liczy się w chwili zgłoszenia wygranej, z listy z tej chwili. Gracz teoretycznie może przed kliknięciem „wygrałem” odznaczyć lub zaznaczyć postać i zobaczyć, czy następny mecz jest łatwiejszy. Łagodzenie, od najtańszego: (a) zapisujemy odcisk składu w logu każdego meczu, więc admin widzi, kto zmieniał skład w trakcie biegu (kolumna `roster_fingerprint`, tanio); (b) UI ostrzega przy zmianie posiadania w trakcie biegu; (c) opcjonalnie później „zablokuj skład na czas biegu” jako ustawienie. W wersji 1 proponuję (a) i (b).
3. **Bramka dostępu jest sprawdzana przy każdym wyniku.** Jeśli gracz w trakcie Hardcore zejdzie poniżej wymaganego składu, zgłoszenie wyniku zwraca `409 roster_below_minimum` (bez zapisania wygranej ani przegranej). Run czeka; może przywrócić skład albo porzucić próbę.
4. **„ID jest osobiste.”** „ID 15” u dwóch graczy to inny perk, jeśli mają różne konta. Poradnik „wybierz 15, 20, 30, 40” działa tylko dla graczy z identycznym składem. UI pokazuje obok ID nazwę i ikonę.

### Co jest funkcją czego
Następny mecz to czysta funkcja `(poprzedni mecz, [mecz sprzed dwóch, pamięć], rozmiary list)` na pozycjach. Warstwa żywego składu tylko tłumaczy ID z bazy ↔ pozycje.

### Gwarancje (testy własności)
- 4 różne perki w zakresie puli danej strony i postać w zakresie w każdym meczu, także przy minimalnych pulach (1 postać, 4 perki).
- Determinizm przy niezmienionym składzie; kolejność klikania perków nie ma znaczenia.
- Hardcore+: każda postać strony raz na rundę N meczów (0 powtórzeń w 25 meczach odznaki przy ≥ 30 postaciach na stronę).
- Żadnego losowania i żadnego hasha w łańcuchu.

### Stabilność w czasie
Po każdym meczu zapisujemy **wyliczony loadout** (ID z bazy; nazwy i ikony UI bierze z katalogów). `ALGO_VERSION` zapisana w runie przy otwarciu: zmiana wzoru nie przepisze meczów już zagranych ani biegnących runów.

### Co widzi gracz
- W setupie: kalkulator meczu 1 na żywo (`15 + 20 + 30 + 40 = 105, 105 mod 54 = 51 → Postać`) **oraz podgląd meczu 2** (mirror: „te same ID po drugiej stronie → Postać / perki”). Podgląd jest wyliczany przez serwer z bieżących list (Twoja decyzja: tak), więc nie dubluje wzoru w kliencie.
- Reguła mirror i wzory są w zasadach. Następny mecz serwer zwraca od razu po zgłoszeniu wyniku; animację odsłonięcia robi klient. Osobny `reveal` jak w Chaosie nie jest potrzebny.

## 6. Tryby trudności, odznaki i bramki dostępu

| | **Milestones** | **Hardcore** | **Hardcore+** |
|---|---|---|---|
| Wariant (`variant`) | `milestones` | `hardcore` | `hardcore_plus` |
| Długość | **bez końca** | **bez końca** | **bez końca** |
| Odznaka przy streaku | **50** | **30** | **25** |
| Checkpointy | co **10** meczów (5 + 5): po 10, 20, 30, 40, 50, … | brak | brak |
| Przegrana | streak wraca do ostatniego checkpointu; run odtwarza zapisany mecz checkpointu. Przed pierwszym checkpointem: powrót do setupu | streak = 0, nowa próba, setup | streak = 0, nowa próba, setup |
| Wzór | podstawowy | podstawowy | **Hardcore+** (sekcja 5) |
| Powtórzenia postaci | możliwe | możliwe | **brak w rundzie** (pamięć) |
| Rekord | `best_streak` | `best_streak` | `best_streak` |
| Grafika | `s1` / `k1` | `s2` / `k2` | `s3` / `k3` |
| Wymagania konta | obecne minimum: **≥ 1 postać i ≥ 4 perki na stronę** | patrz niżej | patrz niżej |

### Jak działa odznaka (tryb nieskończony)
- **Moment przyznania:** w `submit_result`, gdy wygrana podnosi `current_streak` do progu (`BADGE_STREAK = {"milestones": 50, "hardcore": 30, "hardcore_plus": 25}`) i dla tego użytkownika i wariantu nie ma jeszcze rekordu. Serwis zapisuje wtedy jeden `ChallengeCompletionRecord(mode="id_please", variant=…, attempts_taken=<numer próby>, matches_played=<mecze od startu runu>, unlocked_characters_count=<postacie obu stron z żywych list>, full_roster=<obie role pełne>)`. **Run się nie kończy** (`status` zostaje `in_progress`), gra trwa dalej.
- **Dlaczego rekord, a nie odznaka liczona na żywo jak Page Streak:** liczona na żywo odznaka (`get_live_roster_badge`) ma sens, bo Page Streak mierzy stan konta, który może się cofnąć. Tu odznaka to osiągnięcie historyczne (50 wygranych z rzędu się nie „odwygrywa”), a rekord jest odporny na przegraną, abandon i reset próby, i od razu pasuje do półki trofeów, plakietek na kartach i historii ukończeń. Przy pierwszym przyznaniu serwis tylko wstawia wiersz, więc nie wymaga to zmian w `routes/challenge_completions.py`.
- **Jednokrotność:** jeden rekord na użytkownika i wariant (sprawdzany w tej samej transakcji, z blokadą wiersza runu). Dalszy streak (51, 52, …) odznak nie dokłada; liczy się `best_streak`.
- **Reset admina** (`challenge_reset.py`, panel użytkownika w adminie) **kasuje run, jego logi i wszystkie rekordy ukończeń w tym wariancie**, czyli także odznakę (tak działa dla każdego trybu: „plakietka i najlepszy streak znikają”). Zamierzone przy oszustwach; gracz dostaje e-mail. Po resecie może odznakę zdobyć ponownie (decyzja 4).
- **UI:** pasek postępu pokazuje drogę do progu odznaki (np. „17 / 30”), a po jego osiągnięciu zmienia się w licznik rekordu z ikoną odznaki. Konfetti przy pierwszym osiągnięciu progu.

### Bramki dostępu (sprawdzane na żywo)
Perki „zawsze dostępne” `A` liczone z bazy (dziś: killer 19, survivor 17); każda postać uczy 3 perków.

| Tryb | Survivorzy | Killerzy | Perki survivora | Perki killera |
|---|---|---|---|---|
| Milestones | ≥ 1 | ≥ 1 | ≥ 4 | ≥ 4 |
| Hardcore | ≥ 25 | ≥ 20 | ≥ `A_s + 3·25` = **92** | ≥ `A_k + 3·20` = **79** |
| Hardcore+ | ≥ 30 | ≥ 30 | ≥ `A_s + 3·30` = **107** | ≥ `A_k + 3·30` = **109** |

- Wartości w tabeli wyliczają się z `A` i stałych (`HARDCORE_SURVIVORS = 25`, `HARDCORE_KILLERS = 20`, `HARDCORE_PLUS_CHARACTERS = 30`, `PERKS_PER_CHARACTER = 3`), więc nowy zawsze-dostępny perk po patchu sam podniesie próg o 1.
- Wymóg perków jest dodatkowym zabezpieczeniem: zwykle wynika z liczby postaci, ale gracz mógł odznaczyć pojedyncze perki.
- **Odpowiedź API:** `GET /eligibility` zwraca dla każdego trybu `{met, killer: {characters: {have, need}, perks: {have, need}}, survivor: {...}}`. `GET /run` też dołącza `eligibility` dla swojego trybu. `POST /opening` i `POST /result` sprawdzają bramkę po stronie serwera (`409`).
- **UI:** kafelek zablokowanego trybu w modalu pokazuje postęp („Survivorzy 18/25 · Killerzy 20/20 · Perki 80/92”) i link do strony posiadania. `ChallengeIntroTile` ma już `disabled` i `disabledBadge` (sprawdzone w kodzie), więc nowe propsy nie są potrzebne.
- Kolejność trudności w UI: `['milestones', 'hardcore', 'hardcore_plus']`. Czy odznaka wyższego tieru zalicza niższe (`cascadeCompletedTiers`), to decyzja 3 w sekcji 11 (rekomendacja: nie).

Uwagi:
- **Powtórka tego samego otwarcia po przegranej jest dozwolona** (Twoja decyzja). Skutek uboczny: po przegranej w meczu 14 Milestones gracz *wie*, co czeka w 11–14 po powrocie do checkpointu. Akceptowane.
- Blokady otwarcia po ukończeniu (z pierwszej wersji planu) **nie ma**: tryby są nieskończone, a odznaka jednorazowa.

## 7. Model danych

Nowy plik `backend/app/models/id_please.py` (migracja `0033`, obecna głowa to `0032_user_preferences`):

```
IdPleaseRun(StreakRunMixin, ColumnDictMixin["IdPleaseRunDict"], Base)
  __tablename__ = "id_please_runs"
  UniqueConstraint("user_id", "difficulty")      # difficulty: "milestones" | "hardcore" | "hardcore_plus"
  difficulty          String(20)
  algo_version        Integer                    # wersja łańcucha, zapisana przy otwarciu
  opening_side        String(20) null            # "survivor" | "killer"
  opening_perk_ids    JSON_LIST                  # 4 ID perków z bazy (audyt, statystyki)
  current_match       Integer                    # 0 = setup, 1+ = numer meczu w toku (== current_streak + 1)
  current_loadout     JSON_DICT                  # {number, side, character_id, perk_ids[4]}  (ID z bazy, role-scoped)
  before_loadout      JSON_DICT                  # Hardcore+: mecz sprzed bieżącego (ta sama strona co następny mecz); {} gdy brak
  used_character_ids  JSON_DICT                  # Hardcore+: {"killer": [ids], "survivor": [ids]}
  checkpoint_loadout  JSON_DICT                  # Milestones: mecz startowy odcinka po ostatnim checkpoincie; {} gdy brak

IdPleaseMatchLog(StreakLogMixin, ColumnDictMixin["IdPleaseMatchLogDict"], Base)
  __tablename__ = "id_please_match_logs", __run_table__ = "id_please_runs"
  match_number Integer, side String(20), character_id String(100) (nazwa, jak w innych logach),
  perks JSON_LIST, roster_fingerprint String(40)  # odcisk składu z chwili meczu
```

- `StreakRunMixin` daje `current_streak`, `best_streak`, `last_checkpoint_streak` i całe `RetryableRunMixin` (`attempts`, `attempt`, `total_wins/losses`, `playthrough_matches`, `abandon_attempt()`). `ChallengeRunMixin` ma już `user_id` z `ondelete="CASCADE"`, a `MatchLogMixin` klucz `run_id` z `CASCADE`, więc **usunięcie konta** (własne i przez admina) czyści runy i logi bez kodu (test w sekcji 10).
- **Pułapka `_reset_to_fresh`.** `StreakRunService._reset_to_fresh` (abandon, powrót do setupu) przepisuje *każdą* kolumnę z `_build_run` albo z **jawnego, skalarnego** `default`; kolumna bez jednego i drugiego rzuca `RuntimeError`. Domyślne `list`/`dict` (wywoływalne) nie są skalarne, więc `_build_run` musi jawnie ustawić **wszystkie** kolumny JSON (`opening_perk_ids=[]`, `current_loadout={}`, `before_loadout={}`, `used_character_ids={"killer": [], "survivor": []}`, `checkpoint_loadout={}`). Test: abandon każdego z trzech wariantów po kilku meczach (istniejący `test_streak_run_service_shared.py` jest wzorem).
- **Brak kolumn snapshotu**, brak `cleared_openings`, brak zmian w `_KEPT_ON_ABANDON`.
- Run **nie ma długości docelowej** i nigdy nie dostaje `status = completed`; zawsze `in_progress`. Odznakę zapisuje osobny `ChallengeCompletionRecord` (sekcja 6). `attempts` rośnie z każdą porażką (tryb się nie kończy, więc nie jest zerowane), `attempts_taken` w rekordzie odznaki = `attempts + 1` w chwili osiągnięcia progu.
- Stałe: `BADGE_STREAK = {"milestones": 50, "hardcore": 30, "hardcore_plus": 25}`, `CHECKPOINT_INTERVAL = {"milestones": 10, "hardcore": 0, "hardcore_plus": 0}`.
- `used_character_ids` jest zerowane per strona, gdy zagrano wszystkie postacie tej strony (nowa runda pamięci Hardcore+).
- **Stan łańcucha nie zależy od logów.** `add_match_log` przycina logi do 100 na run (`MAX_LOGGED_MATCHES`, admin może obniżyć przez `match_log_max_entries`), a przy streaku 150 logi z początku biegu znikną. Cały stan potrzebny do następnego meczu (`current_loadout`, `before_loadout`, `used_character_ids`, `checkpoint_loadout`, `current_streak`) leży w wierszu runu, a logi służą tylko do podglądu i statystyk.

### Serwis `IdPleaseService(StreakRunService)`
- `mode = "id_please"`, zmienna wariantu = `difficulty`. `get_or_create_run`, `abandon_run`, `get_stats`, `get_completions` są dziedziczone; `_present` dokłada `phase`, `badge`, `eligibility`, odcisk i rozwiązany loadout.
- `_build_run`: pusty run w setupie, **wszystkie kolumny jawnie** (sekcja 7). Brak `_refresh_if_untouched` i snapshotów (`_is_untouched`/`_pool_is_stale` zostają domyślne `False`).
- **Kill switch:** `assert_challenge_mode_enabled("id_please")` jest dziedziczone w `_get_or_create_run` (tworzenie runu) i `_abandon_run`; `submit_opening` i `submit_result` wołają go jawnie (jak Gauntlet i Chaos). Wyłączony tryb: brak nowych runów, otwarć, wyników i abandonów; odczyty (`/run` istniejącego runu, `/stats`, `/completions`, `/roster`, `/preview`, `/eligibility`) zostają, a strona i tak jest za `ChallengeModeGate`.
- `submit_opening(user_id, run_id, side, perk_positions, roster_fingerprint)`: kill switch; blokada wiersza; run musi być w setupie; bramka dostępu (`409 roster_below_minimum`); odcisk zgodny z bieżącym (`409 roster_changed`); 4 różne liczby całkowite w zakresie listy perków strony; wylicza mecz 1; zapisuje `opening_*`, `algo_version`, `current_match = 1`, `current_loadout`; w Hardcore+ zaczyna pamięć (`used_character_ids[side] = [postać meczu 1]`).
- `submit_result(user_id, run_id, match_number, result)`, kolejność kroków w jednej transakcji:
  1. kill switch;
  2. `_load_run_for_result` (blokada wiersza, własność runu);
  3. **`match_number` musi równać się `current_match`**, inaczej `409 stale_match`. To zabezpiecza przed podwójnym kliknięciem i dwiema kartami: bez tego dwa żądania „win” pod rząd przeskoczyłyby dwa mecze, bo klient nie przysyła, o który mecz chodzi (inaczej niż Chaos, gdzie `killer_id` już-wyczyszczony daje błąd);
  4. bramka dostępu (`409 roster_below_minimum`, bez zapisu wyniku);
  5. **wygrana:** `current_streak += 1`, `best_streak`, `add_match_log` (liczniki + przycinanie), odcisk składu w logu; jeśli streak właśnie równa się `BADGE_STREAK[difficulty]` i nie ma jeszcze rekordu tego wariantu, `record_challenge_completion(...)` w tej samej transakcji; w Milestones co `CHECKPOINT_INTERVAL` zapis `last_checkpoint_streak` i `checkpoint_loadout` (mecz, który właśnie wylosowano jako następny); następny mecz z `chain` na **żywych** listach, zapis `before_loadout` (Hardcore+) i `used_character_ids` (z zerowaniem rundy);
  6. **przegrana:** log, `start_new_attempt()`; Milestones z checkpointem > 0: `current_streak = last_checkpoint_streak`, `current_loadout = checkpoint_loadout`; w pozostałych przypadkach powrót do setupu (`current_match = 0`, `opening_*`, `before_loadout`, `used_character_ids`, `checkpoint_loadout` wyczyszczone, `best_streak` zostaje).
  Serwer sam decyduje o postaci i perkach; klient wysyła tylko `run_id`, `match_number` i `win/loss`.
- `apply_inactivity_loss(run_id, idle_before)`: przez `load_idle_run_locked`; **nic nie robi dla runu w setupie** (`current_match == 0`: nie ma czego przegrywać, a `updated_at` nie byłby podbity, więc run wracałby do każdego przebiegu); w grze liczy przegraną z `triggered_by = "inactivity"`, **bez bramki dostępu** (nie może rzucać 409) i bez liczenia nowego meczu (tylko powrót do checkpointu albo setupu).
- Odznaka: `full_roster` = prawda, gdy `get_full_roster_milestone` zwraca prawdę dla obu ról (wołamy dwa razy); `unlocked_characters_count` = postacie obu stron z żywych list; `matches_played` = `total_wins + total_losses`. Rekord jest dodawany do sesji (`record_challenge_completion` tylko `db.session.add`), więc commit wykonuje ta sama transakcja co aktualizacja runu.

```python
from bisect import bisect_left
from dataclasses import dataclass

LOADOUT_PERKS = 4
OTHER = {"killer": "survivor", "survivor": "killer"}


@dataclass(frozen=True)
class Sizes:
    killer_characters: int
    killer_perks: int
    survivor_characters: int
    survivor_perks: int

    def characters(self, side: str) -> int:
        return self.killer_characters if side == "killer" else self.survivor_characters

    def perks(self, side: str) -> int:
        return self.killer_perks if side == "killer" else self.survivor_perks


@dataclass(frozen=True)
class Match:
    number: int                 # 1-based; after a win it is also the streak
    side: str
    character: int              # position in the side's current character list
    perks: tuple[int, ...]      # 4 distinct positions in the side's current perk list, ascending


def fit(values, size):
    """Put values into 0..size-1 with `mod size`; a clash moves up by one. Always 4 distinct results."""
    taken = []
    for value in values:
        value %= size
        while value in taken:
            value = (value + 1) % size
        taken.append(value)
    return sorted(taken)


def first_match(side, perks, sizes):
    return Match(1, side, sum(perks) % sizes.characters(side), tuple(sorted(perks)))


# --- Milestones and Hardcore -------------------------------------------------
def next_match(previous, sizes):
    side = OTHER[previous.side]
    streak = previous.number                       # wins so far in this attempt
    size, characters = sizes.perks(side), sizes.characters(side)
    mirror = fit(sorted(previous.perks), size)     # the same IDs on the other side
    if streak == 1:                                # match 2: the plain mirror
        return Match(2, side, sum(mirror) % characters, tuple(mirror))
    total, last = sum(mirror), previous.character
    raw = [mirror[j] * (streak + 2) + total + j * (last + 1) + streak * streak for j in range(LOADOUT_PERKS)]
    perks = fit(raw, size)
    character = (sum(perks) * (streak + 1) + last + total) % characters
    return Match(streak + 1, side, character, tuple(perks))


# --- Hardcore+ ---------------------------------------------------------------
def next_match_plus(previous, before, used, sizes):
    """`before` = the match two back (same side as the new one) or None for match 2;
    `used` = positions of characters already played on the new side in this attempt."""
    side = OTHER[previous.side]
    s = previous.number
    size, nchars = sizes.perks(side), sizes.characters(side)
    mirror = fit(sorted(previous.perks), size)
    if s == 1:                                   # match 2: plain mirror, as in the other modes
        c = sum(mirror) % nchars
    else:
        u, cu = before.perks, before.character   # loadout and character two back
        total, last = sum(mirror), previous.character
        raw = []
        for j in range(LOADOUT_PERKS):
            a, b = mirror[(j + 1) % 4], mirror[(j + 2) % 4]
            raw.append(mirror[j] * (s + 2) + a * b + u[(j + s) % 4] * (s + 3) + s ** 3
                       + total + j * (last + 1) + cu * (j + 2))
        mirror = fit(raw, size)
        c = (sum(mirror) * (s + 1) + total * (cu + 1) + last * s + sum(u) + s * s) % nchars
    if len(used) >= nchars:
        used = set()
    while c in used:
        c = (c + 1) % nchars                     # next free character
    return Match(s + 1, side, c, tuple(mirror))


# --- Live roster layer: DB ids <-> positions in the CURRENT sorted owned list ----
def to_pos(db_ids, owned):
    """Position of each id in the current list; a no-longer-owned id lands on its nearest higher neighbour."""
    return [min(bisect_left(owned, i), len(owned) - 1) for i in db_ids]


def to_ids(positions, owned):
    return [owned[p] for p in positions]
```

Zerowanie pamięci Hardcore+ robi **wywołujący** (serwis), a funkcja jest czysta. Pętla odniesienia użyta w testach:

```python
def play_plus(side, perks, sizes, n):
    chain = [first_match(side, perks, sizes)]
    used = {"killer": set(), "survivor": set()}
    used[side].add(chain[0].character)
    while len(chain) < n:
        m = next_match_plus(chain[-1], chain[-2] if len(chain) > 1 else None, used[OTHER[chain[-1].side]], sizes)
        if len(used[m.side]) >= sizes.characters(m.side):
            used[m.side].clear()                 # every character played once: a new round starts
        used[m.side].add(m.character)
        chain.append(m)
    return chain
```
